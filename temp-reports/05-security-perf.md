# Security, Performance & Architecture Audit

**Project:** opencode-gui (Tauri v2 + React, Windows-only)
**Date:** 2026-08-30
**Scope:** `src-tauri/src/lib.rs`, `src/lib/plugins.ts`, `src/hooks/usePlugins.ts`, `src/components/FileTree.tsx`, `src/components/FileEditor.tsx`, `src/api.ts`, `src/components/MessageList.tsx`, `src/hooks/useOpencode.ts`, `src/lib/sessionStore.ts`, `src/components/Terminal.tsx`, `src-tauri/src/pty.rs`, `tauri.conf.json`, `capabilities/default.json`, plus cross-cut scans (`innerHTML`/`eval`/`CSP`/`localStorage`/`fetch`/`http_json`)
**Auditor:** automated code review (line numbers verified against current HEAD)

---

## Overview

The app is a thin desktop wrapper around an `opencode serve` sidecar on `127.0.0.1:<random>`. The Tauri host owns the sidecar lifecycle and exposes ~30 `#[tauri::command]`s for file, PTY, plugin, browser and system functions. The frontend talks to the sidecar over HTTP/SSE and persists almost all state in `localStorage` under `oc.*`.

**Headline risks:**

* **No filesystem sandbox.** Every `file_*` / `write_file` command accepts an arbitrary absolute Windows path and writes/deletes/renames it with the user's privileges — a compromised renderer or a malicious plugin can overwrite any file the user can write. This is the single highest-severity architectural mistake. (`lib.rs:435-553`)
* **No CSP at all** (`tauri.conf.json:28` `csp: null`). Combined with four `dangerouslySetInnerHTML` sinks and unsandboxed plugin code execution, any XSS becomes remote code execution via `invoke`.
* **Plugin host is `eval`-equivalent.** `main.js` is turned into a Blob URL and `import()`-ed with full `invoke`/`h`/`React` privileges and raw CSS injection — no sandbox, no signature, no allow-list. The catalog is fetched from GitHub with no hash pinning. (`src/lib/plugins.ts:232-271`, `src/lib/pluginsCatalog.ts:45-90`)
* **HTTP allowlist bypassable by prefix.** `http_json` checks `url.starts_with("http://127.0.0.1")` etc., so `http://127.0.0.1.evil.com` passes. Header names/values are forwarded unchecked.
* **Unbounded in-memory growth** in `sessionStore`, `useFileCache`, and the per-session SSE stores — long sessions or many workspaces OOM the renderer with no eviction.

Overall posture: appropriate for a trusted-local-tool, not for handling untrusted content. Every fix below preserves the current UX; most are a few lines.

## Category Deep Dives

### Security — Injection / XSS / Path Traversal / Plugin Sandbox

**Path traversal (S01, S02, S14, S15).** Every `#[tauri::command]` that touches the filesystem (`write_file:436`, `file_create:444`, `file_delete:458`, `file_rename:466`, `file_duplicate:476`, `file_reveal:510`, `file_open:540`) does `std::fs::write(&path, content)` on the raw string from the WebView with only an `is_empty` check. `plugin_remove:617-637` and `plugin_install_files:640-672` are the only file commands that validate (`..`/`/` check + `canonicalize` + `starts_with(plugins_dir)`). The fix is to generalize that pattern. On Windows, also canonicalize `\\?\` verbatim paths and reparse trailing `..` after `join`.

**HTTP SSRF / allowlist bypass (S03, S04).** `http_json:363-384` is the only network egress for plugins. The current `starts_with` allowlist was already flagged in `temp-reports/01-hardcoded.md:213`. Confirming: `url.starts_with("http://127.0.0.1")` matches `http://127.0.0.1.evil.com` because `String::starts_with` is literal. The fix is a one-function `is_allowed_url(&Url)` with CIDR checks.

**XSS (S05, S11, S12).** `react-markdown` without `rehypeRaw` is safe by default — confirm no `rehypeRaw` is imported anywhere (grep for `rehype-raw` yields zero). The four `dangerouslySetInnerHTML` sites are therefore the only XSS surface, and they all gate through `hlHtml`/`escPlain`. The defence is correct but brittle: a single future change adding `rehypeRaw` or returning raw `out` from `prettyJson` would open stored XSS from LLM output (LLM is untrusted). Adding a regression test and a code comment is the cheapest hardening.

**Plugin sandbox (S06, S07, S08).** The host's comment at `src/lib/plugins.ts:6` — "Plugins are trusted local code — they run with app privileges" — is honest. The audit's point is that the install flow (`PluginsDialog` "Install from URL") makes them *remote* code. A user pasting a GitHub URL from a blog post is indistinguishable from a trusted local folder. Mitigation priority: signature/hash verification before `import()`. Secondary: scope `invoke` per plugin (e.g. `allow: ["http_json","theme_config_read"]` declared in `plugin.json`).

**PTY (S09).** The terminal is a deliberate RCE surface (user asked for a terminal). The concern is *ambient* RCE: any XSS/plugin can `invoke("pty_spawn",{shell:"…",args:["/c","…"]})` without user consent. Gating `pty_spawn` behind the same workspace sandbox and behind an explicit permission (or at least a user-visible "Terminal spawned by plugin '…'" toast) reduces blast radius.

### Performance — Memory / Rendering / Network

**Memory (P01, P03).** The app is optimized for streaming correctness (`sessionStore` flush logic, `busyTracker` grace window) but not for retention. A day-long session with heavy tool use (file reads, diffs) can push each `Msg.parts[]` to hundreds of items with base64 `file.url` payloads. Because `setFetched` (line 147) sorts and retains all messages, the renderer heap grows linearly with session age. No eviction, no persistence to IndexedDB, no virtualization of the message list (all `rowVisible` rows are rendered, `MsgRow` is memoized but not windowed). Recommendation: virtualize `MessageList` with `@tanstack/react-virtual` (already no new dep? would be new dep — so at least cap and add "Load older" pagination).

**Rendering (P04, P05).** The find-in-chat DOM walk is the worst rendering hotspot: it runs outside React, mutates text nodes, and re-walks on every keystroke. The composer highlight is second. Both are fixable with debouncing and `useDeferredValue`.

**Network (P02).** The SSE design (one `EventSource` per workspace) is sound and documented at `src/hooks/useOpencode.ts:844-861`. The gap is resilience: `onerror` does not adjust `liveCount`, so the UI can show "live" while disconnected, and tight reconnect can flood the sidecar on restart. The 2 s poll that adds/removes streams should be replaced by an explicit `workspaces` change listener (already available via `storage` event) to avoid polling.

### Architecture

**Validation belongs in Rust (A01).** The current split — "frontend resolves paths, Rust trusts them" — is the root cause of S01/S02/S14/S15. Tauri's security model expects the opposite: the frontend is untrusted, Rust is the policy enforcement point. Centralizing validation in one `sandbox` module makes the audit surface one function instead of six commands.

**Two workspaces sources (A02).** `localStorage oc.settings.workspace` (written by `useSettings.ts`) and `~/.config/.opencode-gui/workspace` file (written by Rust `workspace_set`) are synced ad-hoc in `main.tsx:19-37`. If they diverge, the sidecar's `current_dir` (set once at spawn from the file) and the frontend's `?directory=` diverge, causing file-tree vs prompt workspace mismatch. Make Rust's file the source of truth and have the frontend read it via `workspace_get` on boot, not via `localStorage`.

**State duplication (A03).** `useOpencode.ts` is ~1300 lines owning seven parallel maps plus an external `createSessionStore` plus a `createBusyTracker`. The `storeRef`/`busyRef`/`sessionDirRef` trio are updated imperatively outside React. This is the file most likely to harbor the next race bug (e.g. `openSession:628-651` `if (busyRef.current.has(id)) return` races with SSE). Refactor incrementally: extract `useWorkspaceSessions(dir)` and `useAttention(permissionsRef, questionsRef)`.
